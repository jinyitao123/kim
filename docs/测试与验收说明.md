# Validation guide

> 当前适用范围：本总仓 `desktop/` 的固定源码、工具链、构建与包内验证。`scripts/release/` 已随桌面源码集成，检查入口以 `package.json` 为准；实际进展与对应提交证据见[工程管理](../../docs/engineering/README.md)。下文的桌面来源仓分支保护说明不代表本总仓已经采用同一组 GitHub 设置。

This page explains how to reproduce and interpret GooeyPi's validation gates. It is not a status report. A passing command or workflow is evidence only for the exact commit, runner, inputs, and credentials that produced it; do not infer that the current branch is green from this document.

## Recommended `main` branch protection target

The recommended `main` branch protection requires pull requests and successful status checks with **Require branches to be up to date before merging** enabled (`required_status_checks.strict: true`). This page defines the target check set; it does not assert that branch protection is currently active.

For pull requests that change desktop paths, configure these required check contexts:

- `Desktop path filter`
- `Production dependency audit`
- `quality`
- `hermetic-e2e`
- `windows-state-migration`
- `packaging-smoke (macos-14, mac, arm64, --config.mac.identity=null)`
- `packaging-smoke (ubuntu-22.04, linux, x64)`
- `packaging-smoke (windows-2022, win, x64)`

Do not require `local-qa-package`: it is manual local QA, runs only through `workflow_dispatch`, and is intentionally excluded from pull-request validation.

`Desktop path filter` runs on every pull request so desktop checks can be skipped successfully when unrelated paths change. `Production dependency audit` is a required desktop pull-request gate: it runs the exception-aware `npm run audit:production` evaluator against the exact PR head, and the release workflow runs the same evaluator against its validated immutable SHA before any package or publication job. After the check contexts first appear on a pull request, a repository administrator should require the path filter and all applicable desktop gates on `main`. The scheduled [dependency-audit workflow](../../.github/workflows/desktop-audit.yml) remains for advisories disclosed after merge.

GitHub merge queues are not available to this public repository while it is owned by a personal account. Consequently, `merge_group` or a required merge queue cannot enforce this policy here; strict up-to-date branch protection is the supported latest-main control. If the repository moves to an organization, merge-queue support should be designed and tested separately before enabling it.

An authorized maintainer can verify the active legacy branch protection and exact required-context set with:

```sh
gh api repos/jinyitao123/weave-workbench/branches/main/protection \
  --jq '{strict: .required_status_checks.strict, contexts: .required_status_checks.contexts, reviews: .required_pull_request_reviews}'
```

## Reproducible setup

The repository derives its Node and npm policy from checked-in metadata. `package.json#engines`, `package.json#packageManager`, and `.nvmrc` must agree; release entry points reject unsupported, malformed, or prerelease tool versions. With `nvm`, prepare a checkout as follows:

```bash
nvm install
nvm use
npm run toolchain:bootstrap
npm ci
npm run release:preflight:toolchain
```

Run `toolchain:bootstrap` before installing project dependencies. It installs the `packageManager`-pinned npm into the invoked npm's validated global prefix, verifies the exact installed JavaScript CLI with the active Node executable, and publishes the matching shim directory to later GitHub Actions steps. This is necessary because the npm bundled by `actions/setup-node` can be older than the repository's npm floor.

`npm ci` runs the shared `postinstall` entry point. That entry point installs Electron's platform runtime synchronously before asking Electron Builder to rebuild native dependencies, so parallel test workers do not race Electron's lazy downloader. Installing with `--ignore-scripts` intentionally skips both operations; follow the recovery sequence in the [source setup instructions](../README.md#run-from-source) before running or packaging the application.

Do not hard-code the current Node, npm, or Electron version in validation notes. Record the values observed for the tested commit instead.

## Packaging dependency collection

`package.mjs` and unpacked CI builds run [`electron-builder.mjs`](../scripts/release/electron-builder.mjs). This adapter selects electron-builder's bundled filesystem traversal collector for the build process. The npm collector can omit duplicated transitive dependencies with npm 12 and a shared `node_modules` directory. The adapter replaces only the collector factory in memory, does not change installed library files, and rejects an unavailable builder API.

macOS DMG and ZIP verification additionally uses [`verify-runtime-modules.mjs`](../scripts/release/verify-runtime-modules.mjs). It extracts the packaged ASAR, including its unpacked native files, outside the checkout and imports the packaged main's runtime modules with Electron. A missing transitive dependency such as `fs-extra` therefore fails verification even when archive layout, native architecture and signatures pass. This probe does not log in or exercise employee business actions.

Local macOS QA can pass `--output-directory release/mac/arm64-COMMIT` to `package.mjs` to preserve earlier artifacts. Custom output must be a new directory inside `release/`; Linux and Windows keep their standard output and verification paths. `--skip-verify` retains its existing requirement that the applicable upstream quality and E2E checks have already passed.

## Pull-request and branch CI

The [CI workflow](../../.github/workflows/desktop-ci.yml) runs on pull requests, pushes to `main`, and manual dispatch. Each Node job bootstraps the repository npm before `npm ci` and executes the toolchain-only release preflight after installation.

| Job | When it runs | What a pass establishes |
|---|---|---|
| `desktop-path-filter` | Pull request, `main`, manual dispatch | Detects changes under `desktop/**` or the root desktop workflow files; this check always runs so skipped desktop jobs do not leave required checks pending. |
| `production-audit` | Pull request or `main` when desktop paths change; manual dispatch | The exception-aware production dependency audit passes for the exact checked-out commit. |
| `quality` | Pull request or `main` when desktop paths change; manual dispatch | TypeScript checks; configured lint and format checks; the coverage suite and thresholds; production bundle creation; bundle-size budgets; coverage artifact upload. |
| `hermetic-e2e` | Pull request or `main` when desktop paths change; manual dispatch | The built application passes the Playwright Electron suite on the pinned macOS runner without relying on developer state. Failure artifacts are uploaded when available. |
| `windows-state-migration` | Pull request or `main` when desktop paths change; manual dispatch | The state migration suite passes on a real `windows-2022` runner, including the production-platform fresh-install, migration, restart, and update path. Simulating `platform: 'win32'` on another OS is useful unit coverage but is not a substitute for this job. |
| `packaging-smoke` | Pull requests with desktop path changes | Native macOS arm64, Linux x64, and Windows x64 runners can build unpacked application directories. Linux and Windows additionally verify the ASAR layout and exact native-unpack allowlist. These are unsigned smoke builds, not public installers. |
| `local-qa-package` | Manual dispatch only | After the same immutable SHA passes quality, production audit, macOS hermetic E2E and native Windows state migration, native runners create and verify installable local-QA artifacts for macOS, Linux, and Windows. The package command skips only the already-passed aggregate; bundle creation and post-package integrity, architecture, native-layout, fuse and size gates remain. This is not a claim that every POSIX-oriented unit fixture ran on Windows or that the artifacts are signed public releases. |

Expected skips are part of this design:

- `local-qa-package` is expected to be skipped on pull requests and pushes to `main`.
- `packaging-smoke` is expected to be skipped on pushes to `main` and manual dispatches because its condition is pull-request-only.
- All desktop validation jobs except `desktop-path-filter` are skipped successfully when neither `desktop/**` nor a root desktop workflow file changed.

`windows-state-migration` runs whenever a desktop path changes; it is expected to be skipped successfully for unrelated repository changes.

A green PR packaging matrix does not prove Developer ID signing, Apple notarization/stapling, Gatekeeper acceptance, Authenticode identity, installer integrity, or the complete public artifact matrix. Those belong to the release workflow.

## Local aggregate commands

Use focused tests while developing, then choose the aggregate that matches the claim you need to make. The command definitions in [`package.json`](../package.json) remain authoritative.

| Command | Scope |
|---|---|
| `npm run release:verify:package` | Toolchain preflight, typecheck, configured code checks, coverage tests, production bundle, and bundle-size gate. It does not create an installer or run Electron E2E. |
| `npm run release:verify` | The package-verification aggregate above plus the hermetic Electron E2E suite. |
| `npm run test:e2e` | Builds the application, then runs the hermetic Electron E2E suite. |
| `npm run audit:production` | Fetches npm's production audit report and applies the repository's high/critical advisory and exception policy. Network access is required. |
| `npm run package:mac:local-qa` | On macOS, runs the relevant verification aggregate, creates unsigned/unnotarized DMG and ZIP artifacts, and applies macOS post-package checks in QA mode. |
| `npm run package:linux:local-qa` | On Linux, runs the package-verification aggregate, creates the configured Linux artifacts, and verifies their runtime layout in QA mode. |
| `npm run package:win:local-qa` | On Windows, runs the package-verification aggregate, creates the configured Windows artifacts, and verifies their runtime layout in QA mode. |

Packaging is native: run each platform command on its matching operating system and architecture. The public `package:mac`, `package:linux`, and `package:win` commands use distribution mode; macOS and Windows distribution checks require their external signing configuration. A successful local-QA command must not be described as a public trust check.

## Dependency audit policy

The [dependency-audit workflow](../../.github/workflows/desktop-audit.yml) runs weekly and on manual dispatch. It uses the repository toolchain and executes `npm run audit:production` against the production dependency graph. This scheduled job supplies advisory coverage for vendored package forms that Dependabot cannot parse.

Ordinary PR CI validates the exception file and its expiry rules, but it does not replace the live registry-backed audit. Use the scheduled or manually dispatched audit workflow when making a current dependency-advisory claim.

The project gate and raw npm output answer different questions:

- `npm audit --omit=dev` is the underlying registry report for the production lock graph. Its output and exit status are diagnostic and can change as the advisory database changes.
- `npm run audit:production` parses that report and fails on every unaccepted **high** or **critical** advisory.
- [audit-exceptions.json](../scripts/release/audit-exceptions.json) can accept an exact advisory/package pair only with a reason and expiry. The gate also fails expired exceptions and stale exceptions that no longer match the report.
- The ordinary release-script tests check exception structure and expiry, so an elapsed acceptance is visible in PR CI as well as in the weekly audit.

A passing audit therefore does not mean the production graph carries no known advisory: the gate also passes while an advisory is accepted in [audit-exceptions.json](../scripts/release/audit-exceptions.json) with a reason and an unexpired date. Never restate a passing gate as "zero vulnerabilities". Read that file for the accepted-risk position at the commit under review, and treat adding or extending an exception as a security-sensitive change governed by the [dependency pinning and supply-chain policy](安全模型.md#dependency-pinning-and-supply-chain).

## App-private runtime validation

RC5 adds pinned Node, Pi, Prime and npm under `resources/runtime` so a fresh employee machine does not require global CLI installations. `runtime-lock.json` and the independent runtime npm lock identify the executable distributions and dependency closure. The normal electron-builder wrapper prepares this closure, verifies it, and runs offline probes on a native target. `afterPack` compares the actual package tree with the external prepared manifest before applying the unchanged Electron fuses.

Only parsed Source Map v3 `.map` documents and zero-byte `.gitkeep` repository placeholders are removed before sealing the runtime manifest. Nonempty `.gitkeep` files are retained. Types, documentation, executable code and native libraries remain present; unknown `.map` data is retained. The manifest records the pruning policy and removed inventory digest. Runtime verification applies to the post-pruning tree.

Package metrics retain the original **480 MiB application budget excluding `resources/runtime`**, introduce an explicit **384 MiB runtime content budget**, and cap the complete app at **864 MiB**. All three byte totals must be reported separately. This makes the newly embedded runtime cost visible instead of weakening the original application or JavaScript bundle limits. The existing `app.asar` and source-bundle ceilings remain unchanged. Compressed installer limits are independently checked and are not implied by these uncompressed limits.

Runtime profiles are app-owned directories, not an operating-system sandbox. HOME and user Git configuration are not redirected; model credentials, agent/session/plugin roots, npm configuration/cache, and implicit cloud credential files use explicit private paths. The reviewed Prime vendor opt-in disables its shared CLI auth fallback without changing other Prime installations. Empty-profile probes prove isolation and catalog availability only, not a real model request or an enterprise business result.

## Public release validation

The [release workflow](../../.github/workflows/desktop-release.yml) runs only after a manual request names an existing semantic-version tag; pushing a tag does not publish automatically. It first verifies that the tag matches both package manifests and resolves to a commit on `main`; downstream jobs check out the resulting immutable commit SHA.

| Release job | Responsibility |
|---|---|
| `validate` | Enforce the repository toolchain, validate tag/package versions and `main` ancestry, and expose the exact release SHA. |
| `production-audit` | Apply the exception-aware production dependency audit to that immutable SHA before any package job. |
| `quality` | Run `release:verify:package` for that SHA. |
| `hermetic-e2e` | Build and run the Electron E2E suite for that SHA. |
| `package` | Build both native macOS architectures. Credential preflight is fail-closed; public verification checks the signing identity, required microphone entitlements on the app and every Electron helper, the notarization staple on each packaged app, Gatekeeper, artifact integrity, fuses, native layout/architecture, and package budgets. |
| `package-linux` | Build the configured Linux architectures on native runners and apply the Linux package/runtime verification path. |
| `package-windows` | When explicitly enabled, build either Authenticode-signed public packages or unsigned beta packages. Signed mode requires signing secrets and the configured signer subject and/or thumbprint. |
| `release-packages` | Reject failed prerequisites, collect the enabled platform artifacts, generate checksums, attest provenance, and publish or resume the GitHub Release with write permission scoped to this final job. |

Native release jobs pass `--skip-verify` only after the same immutable SHA has passed the upstream quality and E2E jobs. That flag skips a duplicate pre-package test aggregate; it does not skip bundle creation or the platform-specific post-package verification.

Public macOS checks require external Developer ID and notarization credentials that are not present in ordinary PR CI. Signed Windows packaging is also conditional on repository configuration and secrets. If neither signed nor unsigned Windows release mode is enabled, `package-windows` is expected to be skipped and the aggregate release gate explicitly accepts that skip. Within an enabled Windows job, the signed and unsigned build steps are mutually exclusive, so one of them is normally skipped.

An explicitly enabled unsigned Windows beta is not trust-ready and must be labelled as such. Ordinary PR smoke packages and manual local-QA artifacts do not replace any credentialed release check.

## Recording evidence

Keep point-in-time results in the PR, release notes, or another commit-addressed record rather than updating this guide with a new "current status". Record at least:

- the full commit SHA and whether the worktree was clean;
- the workflow run URL or exact commands and exit status;
- runner image or local OS/architecture, plus observed Node and npm versions;
- workflow inputs and which conditional jobs or steps were skipped;
- the audit exception file used for dependency-audit claims;
- artifact names and checksums, and whether each artifact was unsigned, signed, notarized, stapled, or provenance-attested;
- any failure, rerun, accepted limitation, or manual observation needed to interpret the result.

Use test counts only inside that commit-addressed evidence. The durable claim is that the checked-in aggregate completed successfully, not that this guide remembers how many tests happened to exist at some earlier date.

RC5 native arm64 candidate measurement: application 448,933,814 bytes; managed runtime 351,810,206 bytes; complete app 800,744,020 bytes; DMG 263,355,660 bytes; ZIP 265,268,232 bytes. The compressed installer ceilings are each 255 MiB, the next 5 MiB boundary above these measurements. These private QA artifacts are unsigned and do not establish real-server or business-scenario acceptance.
